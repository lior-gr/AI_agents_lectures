B.1 Goal and prerequisites

Define the scope before writing router code.

Goal

Keyword routing alone is often weak for synonyms and disambiguation. Bounded model routing keeps model flexibility while limiting outcomes to a fixed skill enum.

Prerequisites

  • agent.py has a stable loop.
  • skills/always_on.md exists.
  • Optional skill files exist for planning/reporting/output.
  • Runtime OpenAI API key is configured.

Development vs runtime separation

Codex creates or edits skill_router.py and agent.py during development. At runtime, your agent process makes router calls directly. Codex is not in that runtime execution path.

B.2 New term onboarding and system diagram

Learn the term first, then inspect the flow.

New term: Bounded model-assisted routing

Definition: a model classifies intent into a fixed allowed enum, then deterministic validation accepts or rejects the output.

Why it matters: better intent handling than keywords, with bounded safety.

Where in code: skill_router.py and agent.py prompt construction.

Snippet
ok, skills, reason = route_skills_with_model(goal, call_router_model, max_attempts=3)
if not ok:
    skills = []  # always_on still applies
Verification checklist
  • Unknown skill names are rejected.
  • Bad JSON retries until max attempts.
  • Fail state uses always_on only.
  • Main loop and MCP tool logic stay unchanged.

What this diagram illustrates

Routing affects prompt composition only. Agent loop and tools remain unchanged.

Development lane: Codex edits skill_router.py and agent.py | v Runtime lane: User goal text -> bounded router model call -> strict JSON validation -> selected optional skills -> prompt assembly (always_on + selected) -> normal agent loop (unchanged) -> MCP tools (unchanged)

Course example

Goal "print tasks in JSON" can route to status_reporting + output_format if validated. If routing keeps failing, runtime still proceeds with always_on only.

B.3 Bounded routing contract

Declare allowed outputs and reject anything outside the contract.

Allowed optional skill enum

  • task_planning
  • status_reporting
  • output_format

always_on is not routable because it is injected every time.

Strict JSON output shape

{
  "skills": ["task_planning", "output_format"],
  "confidence": 0.82,
  "notes": "One short sentence."
}
Validation rules
  • Must parse as JSON object.
  • Keys must be exactly skills, confidence, notes.
  • skills uses only allowed names and no duplicates.
  • confidence is numeric and in [0, 1].
  • notes is short string (for logs only).

B.4 Implementation prompts

Apply these in order to keep changes bounded and testable.

Prompt 1: Create skill_router.py 
Create skill_router.py with:
- ALLOWED_SKILLS
- route_skills_with_model(goal: str, call_model_fn, max_attempts: int) -> (ok, skills, reason)

Requirements:
- Build routing prompt with allowed enum and short skill descriptions
- Demand JSON only
- Validate JSON deterministically
- Retry until success or fail state
- No keyword fallback
- Standard library only (json, typing)
- ASCII-only strings

Explanation channel contract:
1) In-file comments:
   - validator checks and retry intent
2) Codex chat explanation:
   - safety tradeoffs and failure behavior
3) Both:
   - critical reject conditions (wrong keys, unknown skills, duplicates, non-JSON)
Student verification
  • Confirm invalid JSON is rejected and retried.
  • Confirm unknown skills are rejected.
  • Confirm exports include ALLOWED_SKILLS and router function.
Prompt 2: Add low-cost router model call 
In agent.py, add call_router_model(messages) -> str:
- low temperature (0 or close)
- small max_output_tokens
- return raw text only

Then wire it into route_skills_with_model.
Keep main agent model path unchanged.

Explanation channel contract:
1) In-file comments: why router calls should stay cheap and deterministic
2) Codex chat explanation: cost/latency tradeoff and verification steps
Student verification
  • Confirm router call path is separate and cheaper.
  • Confirm main generation path is unchanged.
  • Confirm logs can show selected skills during testing.
Prompt 3: Integrate prompt construction 
In agent.py prompt construction:
1) Always load skills/always_on.md
2) Route optional skills with route_skills_with_model(..., max_attempts=3)
3) If routing ok, load selected skills from skills/.md
4) If routing fails, load no optional skills
5) Concatenate with "\\n\\n---\\n\\n"

Requirements:
- Do not change loop structure
- Do not change tool execution logic
- State in comments: routing affects reasoning only
Student verification
  • Confirm only reasoning input changed.
  • Confirm tool behavior and control flow are unchanged.
  • Confirm fail state still runs safely with always_on only.

B.5 Fail state behavior (no fallback)

Define failure behavior explicitly to avoid hidden routing errors.

  • After max_attempts failures, apply only always_on.
  • Continue normal agent loop.
  • Optional: one-line debug log that routing failed.

This avoids silent misrouting and avoids keyword fallback guessing when classifier output is invalid.

B.6 Practical tests

Run these examples after implementation to validate behavior.

Synonyms

  • Goal: "display my tasks" - expected status_reporting
  • Goal: "print tasks in JSON" - expected status_reporting + output_format

Disambiguation

  • Goal: "add tasks about planning a TV show"
  • Expected: often empty skill selection or low-confidence routing, but no crash.

Mixed intent

  • Goal: "plan today in a markdown table"
  • Expected: task_planning + output_format

B.7 Checkpoint

Confirm control boundaries before using this pattern in production.

Checkpoint questions

  1. Who controls which skills are possible?
    The fixed enum and deterministic validator in router code.
  2. Who validates router output?
    Your deterministic validation function, not the model itself.
  3. What happens if routing fails after all retries?
    Fail state: no optional skills, proceed with always_on only.
  4. Did we change the agent loop?
    No. Loop and tool execution remain unchanged.
  5. At runtime, does Codex call your agent?
    No. Codex is development-time assistance; runtime is separate.
