Lesson 3 - Decoupling with a minimal MCP boundary

In Lesson 2, the agent called local execution directly. In this lesson, we keep the same agent loop and move execution behind a subprocess boundary.

P1 What you will learn in this lesson

These outcomes define what done means for MCP decoupling.

By the end of this page, you should be clear on:

  • Why MCP separates execution from agent reasoning and control flow.
  • How to build a minimal deterministic MCP server over stdin/stdout.
  • How to add an MCP client and rewire only the execution layer.
  • How to prove loop logic, stop conditions, and token handling remain unchanged.
  • Why this local pattern scales to remote and enterprise setups later.

P2 What changes and what stays the same

This lesson adds a boundary, not a new planning model.

What stays the same

  • agent.py loop ownership.
  • Step counter and stop conditions.
  • OpenAI call path and token controls.
  • storage.py and tasks_db.json.

What changes

  • Execution moves from direct local calls to an MCP client/server boundary.
  • The agent sends tool requests through mcp_client.py.
  • mcp_server.py handles dispatch and calls storage internally.

Simple example

The user asks to list tasks. The agent still decides to call list_tasks. Only the execution path changes from local function call to MCP message.

P3 Why MCP exists

MCP gives a stable execution contract independent from the agent loop.

  • Decouples tool execution from agent runtime logic.
  • Enables tools to run in separate processes and potentially separate hosts.
  • Supports shared tool infrastructure across multiple agents.
  • Creates a clear place for policy, auditing, and reliability controls later.

In this local lesson, MCP may feel heavier than direct calls. That is intentional: we are training architecture discipline.

P4 Minimal local MCP design

Keep it synchronous, deterministic, and easy to inspect.

  • One Python server process for tool dispatch.
  • JSON request/response messages over standard IO.
  • No networking, no async framework, no background scheduler.
  • Strict error handling with deterministic response structure.

P5 Architecture and message format

Two concrete views: runtime flow and message contract.

main.py -> agent.py -> mcp_client.py -> (JSON over stdio) mcp_server.py -> storage.py -> tasks_db.json

Request message

{
  "tool": "add_task",
  "arguments": { "text": "Buy milk" }
}

Response message

{
  "status": "ok",
  "result": "..."
}

P9 Critical insight

If this lesson is implemented correctly, only execution plumbing changes.

You should not change:

  • Loop logic.
  • Stop conditions.
  • Step counter.
  • Token handling strategy.

P10 What this teaches and scope

Same mental model now, scalable architecture later.

What this teaches now

  • Agent does planning/control; MCP executes tools.
  • Execution can move out-of-process without changing agent reasoning flow.
  • Storage remains unaware of agent or MCP details.

Enterprise features we are not using in this course

  • Remote MCP servers: tools can run on separate hosts/services.
  • Auth and policy gates: enforce identity and operation permissions.
  • Shared tool registries: many agents use the same execution fabric.
  • Centralized observability: aggregate logs, traces, and reliability metrics.

We exclude these now to keep focus on the core decoupling model.

P11 Checkpoint and next lesson

Use these to verify architectural understanding before moving on.

  1. Did the agent loop change in this lesson?
    No. Only execution plumbing should change.
  2. Who executes tools now?
    The MCP server executes tool requests; the agent orchestrates the loop.
  3. Does the MCP server know anything about OpenAI?
    No. MCP server is model-agnostic execution infrastructure.
  4. Can multiple agents reuse the same MCP server design?
    Yes. That is one of the main benefits of decoupling execution.
  5. Is storage aware of agent or MCP?
    No. Storage should stay unaware and only manage data persistence.
