P2 Vocabulary

Definitions first. Precise wording helps later decisions.

Codex plugin in VS Code (development assistant)

  • Codex is software running as a VS Code plugin/extension.
  • Can read and edit your workspace.
  • Can run terminal commands (when allowed).
  • Can follow project instructions such as AGENTS.md.
  • Can use skills and interact with MCP-connected tooling.
  • These are Codex development-session capabilities, not runtime planner-agent capabilities.
  • Specialized for code generation and project-file interaction.
  • It is not the application that your users run.
  • The diagram below explains development flow versus runtime flow.

Agent (runtime decision system)

  • Has a goal, chooses actions, observes tool results, repeats.
  • Owns the decision loop.
  • Without a loop, you do not have a true agent.
  • The runtime agent generated in this course is unaware of Codex.

Skill, MCP, Tool

  • Skill: passive reasoning guidance.
  • MCP server: passive tool/resource provider.
  • Tool: concrete deterministic action on system state.
Development flow: You -> VS Code + Codex plugin -> writes project code -> creates runtime agent Runtime flow (after code exists): User -> runtime agent -> skills + MCP -> tools -> system state Important: runtime agent does not use Codex as a tool.

Simple generic runtime example

User: asks for task-planning support.
Runtime agent: decides first step and then updates plan based on results.
Skills + MCP: skills guide the reasoning of the AI/LLM model, MCP exposes task tools.
Tools: agent calls list/add/complete task tools.
System state: saved task data changes based on tool results.

P3 The stack - who does what

Layer clarity makes the next lessons much easier.

Layered responsibility map

  • Human
  • Codex (development assistant)
  • Your runtime agent
  • Skills (reasoning guidance)
  • MCP servers (tool providers)
  • Tools (filesystem, DB, subprocess, APIs)
Codex builds -> runtime agent runtime agent uses -> skills runtime agent calls -> MCP MCP executes -> tools tools affect -> system state

Task-planner example for "tools affect system state"

If the planner agent calls add_task("Book birthday cake"), your tasks storage changes. That data change is the "system state" effect.

P4 Two kinds of agents

This distinction avoids a lot of confusion later.

Type A - Development agent

Codex in VS Code helps you build the system.

Type B - Runtime agent

Your app-side agent handles goals and tool calls at runtime.

Key insight

We use Codex as an assistant to generate code, including runtime-agent code. The runtime agent is a separate system and is not aware of Codex. Codex is part of the development flow, not part of runtime tools/capabilities. Codex does not call the planner agent. It only helps develop it.

P5 Interaction rules

These guardrails keep architecture stable as features grow.

Allowed interactions

  • Codex -> files, terminal, MCP, skills (during development).
  • Agent decides and calls tools.
  • MCP server executes requested tools.
  • Skills shape model reasoning.
  • Tools affect the external world/state.

Conceptually wrong interactions

  • MCP server planning goals.
  • Skills running subprocesses.
  • Agent editing source code directly as a development actor.
  • Codex directly serving end-user runtime requests.

P6 Practical mental example

One scenario that ties agent, skills, and MCP together.

Option 1 - No agent

User says: "Add task: order birthday candles" -> system writes file -> done. No loop, no planning, no agent.

Option 2 - With agent

User says: "Help me prepare my child's birthday party." Agent reads tasks, prioritizes actions, adds missing steps (cake, venue, decorations), checks progress, and iterates.

Where skills fit

Skills provide planning heuristics, time estimation rules, and formatting guidance.

Where MCP fits

MCP exposes operations like reading tasks, creating tasks, or reserving calendar slots. Agent calls MCP, MCP executes tools, returns results.

P7 Scope for this course

What we are intentionally not using in this hands-on track.

Definition - "Enterprise Features"

Enterprise features are capabilities usually needed by large organizations for centralized control, security, and large-scale shared operations.

Enterprise features we are not using in this course

  • Remote MCP servers and centralized auth/policy: tools hosted remotely with organization-wide access control rules.
  • Shared enterprise tool registries: centrally managed catalogs of approved tools for many teams.
  • Multi-user orchestration infrastructure: coordination layers for many users/agents running together.

We stay local-first, practical, and budget-aware.

We exclude these on purpose so you can master core concepts without extra infrastructure complexity.

P9 Checkpoint

Think first, then reveal.

Quick self-check

  1. Does a Skill ever run a subprocess?
    No. A skill is passive reasoning guidance.
  2. Does an MCP server decide when to call tools?
    No. MCP executes requests; the agent decides.
  3. Can Codex be the application that end users run?
    No. Codex is a development-time assistant, not the application your users run.
  4. Who owns the loop in an agent system?
    The runtime agent logic owns the loop.
