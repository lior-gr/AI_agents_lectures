P1 What you will learn in this lesson

These outcomes define what "ready for Lesson 2" means.

By the end of this page, you should be clear on:

  • How to scaffold a Windows-first CLI task manager with Codex.

P2 Mental model

Deterministic now, agent layer later.

User -> CLI (main.py) -> Storage (storage.py) -> tasks_db.json

Simple example

Command: python main.py --add "Buy milk"
Result: one deterministic file update, no planning, no model call.

Why this matters

If the baseline behavior is unclear, later agent behavior becomes hard to debug because you lose the reference.

P3 Setup and scaffold prompt (Windows first)

First prompt: minimal baseline only, no advanced features.

Prompt to paste into Codex 
Create a minimal cross-platform Python CLI project for a task manager.
Requirements:
- Must work on Windows first
- Use argparse
- Store tasks in tasks_db.json
- Create virtual environment instructions
- Add comments explaining each file
- Explicitly support these commands:
  - --add ""
  - --list
  - --complete 
  - --delete  [task_id ...] (gets task IDs from --list output and deletes those tasks)
- For these commands, generate CLI stubs/mockups only:
  - argparse wiring and function placeholders
  - clear TODO comments for each command
  - no real storage/business logic yet
- Explanation contract:
  - In-file comments: explain module purpose, command responsibilities, and non-obvious validation logic.
  - Codex chat response: explain architecture choices, assumptions, and verification steps.
  - Use both channels for behavior that may confuse future maintainers.
Expected output structure:
task_manager/
|-- main.py
|-- storage.py
|-- tasks_db.json (auto-created later)
|-- README.md
`-- requirements.txt (likely empty)
Do NOT implement advanced features yet.
Do NOT fully implement add/list/complete/delete in this step.

  • Confirm command handlers are stubs with TODO markers, not full logic yet.

P4 Baseline architecture boundaries

Keep roles separate now so later layers stay clean.

Separation of concerns in this lesson

  • main.py: parse CLI arguments and dispatch commands.
  • storage.py: read and write task data in JSON.
  • tasks_db.json: data only.

Why this boundary matters later

In later lessons, the agent layer will call tools, tools will call storage, and storage will touch JSON. If these roles are mixed now, later decoupling becomes brittle.

P5 Incremental prompting technique

Ask for one controlled change at a time.

Step 1 prompt 
Replace the --add stub with a real implementation.
Include detailed comments.
Do not implement --list, --complete, or --delete yet.
In-file comments: explain non-obvious logic and validation checks.
In chat: explain what changed and how to test it.
Step 2 prompt 
Replace the --list stub with a real implementation.
Explain how task indexing works.
Do not implement --complete or --delete yet.
In-file comments: explain index rendering rules.
In chat: explain index assumptions and edge cases.
Step 3 prompt 
Replace the --complete stub with a real implementation by task ID.
Keep the behavior deterministic.
Add clear comments for edge cases.
In chat: explain completion-state transitions and verification commands.
Step 4 prompt 
Replace the --delete stub with a real implementation.
Accept one or more task IDs from --list output and delete those tasks.
Return clear feedback when IDs are invalid or missing.
In-file comments: explain multi-ID handling and invalid-ID behavior.
In chat: explain deletion outcomes and how to verify results.
Student task after each step
  • Run the command added in that step and confirm deterministic behavior.
  • Check that no unrelated features were introduced.
  • Review comments for clarity and correctness.
  • Commit only after each step is verified.

P6 Why no agent yet

This lesson intentionally avoids decision loops.

What we intentionally do not add

  • No agent loop.
  • No model calls.
  • No MCP server.
  • No skills.
Current system: deterministic CLI only User -> main.py -> storage.py -> tasks_db.json No decision-making loop exists.

P7 Checkpoint

Answer before revealing to test your own understanding.

  1. Does this system contain an agent?
    No. It is deterministic command handling and storage updates only.
  2. Where would an agent sit if we add one later?
    Above deterministic tools and storage, as a decision layer that chooses actions.
  3. Should storage ever call OpenAI?
    No. Storage must remain deterministic and model-agnostic.
  4. Is Codex part of runtime for end users?
    No. Codex helps during development; it is not part of runtime execution.
